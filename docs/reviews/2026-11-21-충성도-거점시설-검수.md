## 근거와 결과 요약

정본 링크에서 문서 본문을 가져오지 못했다. 저장소의 [설계서 1단계 사본](../design/phase1-spec.md)은 2단계 충성도·거점 시설 본문을 포함하지 않는다. 아래 태그는 확인 가능한 [006](../tasks/006-loyalty.md), [007](../tasks/007-loyalty-extension.md), [008](../tasks/008-facilities.md)의 것을 인용했다. 유지비는 [002 §9](../tasks/002-roster-and-rules.md#9-유지비-확정), 구현 결정은 [공개 질문 기록](../open-questions.md)을 함께 대조했다. 정본의 문구나 태그가 다르면 해당 판정을 재확인해야 한다.

- 오류 2건. 탐지소 Lv1의 마감 범위가 지시서와 다르고, 가져오기에서 정상 플레이로 만들 수 없는 공사 일정을 받아들인다.
- 문서 공백 3건. 훈련 중 미납, 일부만 낼 수 있을 때 납부 순서, 철수 시 충성도 처리.
- UI·UX 2건. 측정한 주요 버튼은 44px 이상이었다. 충성도 기록과 시설 세부 정보가 한 화면을 차지해 일부 조작은 스크롤이 필요했다.
- 동일 버전·시드·선택에서 저장 왕복 때문에 달라지는 플레이 결과와 용병 영구 소멸은 검사한 경로에서 발견되지 않았다.
- 시설을 사용하는 기본 자동 플레이에서 40회 정산까지 미납이 없었다. 80회까지는 6개 시드 모두 미납이 있었고, `audit-5`에서 76~80일차에 5회 연속 발생했다.

## 오류 1. 탐지소 Lv1 마감 범위가 실제에서 이틀 벗어남

- 종류: 오류
- 심각도: 낮음

### 위치

[`rift.ts:108`](../../src/engine/rift.ts#L108), [`facilities.ts:221`](../../src/engine/facilities.ts#L221)

### 설계서 근거

거점 시설 [확정: 레벨에 따라 정확도 향상]. 008 §1의 임시값은 Lv1 마감 범위를 실제 ±1일로 명시한다. 008의 확정 목록에서 ±1일 자체에 별도 태그는 없다.

### 현상

실제 마감이 6일차인 `r1`에서 기대 범위는 5~7일차다. 실제는 4~6일차로, 한쪽 끝이 실제에서 이틀 벗어난다. 저장 왕복 후에도 같은 범위다.

### 재현 방법

- 시드: `audit-20261120`
- 세이브: `/tmp/arche-main-v5.json` 그대로. `r1.deadlineDay=6`, `r1.fog.deadlineOffset=2`.
- 순서: 불러온 뒤 탐지소 Lv1에서 `r1`의 표시를 확인하거나, 세이브의 `r1`과 `state.facilities`를 `visibleRift(tables, state.facilities, r1)`에 전달한다. 결과 `deadline=[4,6]`.

### 제안

±1일의 대칭 범위가 요구사항이면 마감 계산에 적용한다. 비대칭 범위를 의도했다면 지시서의 ±1일 표현을 정리한다.

## 오류 2. 미래에 시작하는 공사를 v5 불러오기가 받아들임

- 종류: 오류
- 심각도: 낮음

### 위치

[`saveSemantics.ts:205`](../../src/storage/saveSemantics.ts#L205), [`game.ts:496`](../../src/engine/game.ts#L496), [`game.ts:690`](../../src/engine/game.ts#L690)

### 설계서 근거

거점 시설 / 008 §2의 건설 시작 즉시 지불·완료일에 반영, §6의 세이브 의미 검증. 008 확정된 규칙의 건설 비용·기간 항목은 [제안].

### 현상

1일차에 30일차 시작으로 기록된 공사가 이미 진행 중으로 뜬다. 불러오기 검증은 완료일이 시작일 이상인지 검사하며 시작일이 현재일 이후인지 검사하지 않는다. 테스트 복사본은 건설비 차감 없이 31일차에 의무실 Lv1이 됐다. 편집된 JSON으로 재현했으며 정상 조작에서 해당 파일이 생성되는 사례는 발견되지 않았다.

### 재현 방법

- 시드: `audit-20261120`
- 세이브: 원본 복사본의 `state.resources.zero`를 `1000`으로, `state.facilities.construction`을 `{"facilityId":"infirmary","targetLevel":1,"startDay":30,"completeDay":31}`로 바꾼다.
- 순서: 파일을 불러와 거점으로 이동한다. 1일차에 완료까지 30일 남은 공사가 표시된다. 하루를 30번 넘기면 완공 이벤트와 의무실 Lv1을 확인할 수 있다.

### 제안

공사 중인 세이브에서 `startDay ≤ state.day < completeDay`를 검사한다.

## 세이브·결정성·용병 보존

- 007 구현 커밋 `d231dd9`의 실제 v4, 008 구현 커밋 `407ed03`의 실제 v5, 현재 main의 v5에서 각각 `npm run make-audit-save -- audit-20261120 <경로>`로 생성했다. 현재 앱의 스키마·의미 검증으로 세 파일을 읽었다. v4는 v5로 올라가며 탐지소 1, 나머지 0, 공사·배치 없음이 채워진다. 기존 리프트의 흐림 오프셋은 0으로 채우는 구현 결정 때문에 같은 시드로 만든 최신 신규 게임과 표시 범위가 다를 수 있다. 현재 형식은 v5이며 이후 버전 번호를 의도적으로 거절한다. [변환 로직](../../src/storage/saveFile.ts#L37)
- 각 세이브를 출발점으로 80회, 총 240회 정산을 비교했다. 같은 자동 플레이를 한쪽은 메모리에서 계속하고 다른 쪽은 매일 JSON 저장·파싱·의미 검증 후 계속했다. 직렬화 가능한 게임 상태와 당일 이벤트가 매번 일치했다. 전투 보고의 선택 필드에 붙은 `undefined` 속성은 JSON에서 생략되므로 비교도 양쪽을 JSON으로 정규화했다. `npm run days -- 40 audit-20261120` 반복 stdout도 동일했다. 기존 회귀 테스트에는 미납·거부·이탈 및 시설 공사·훈련의 왕복 비교가 있다. [회귀 테스트](../../src/app/determinism.test.ts)
- 위 240회에서 시작 용병 ID 31개가 모두 보존됐다. 이탈을 강제할 조건을 확인하기 위해 별도 v5 복사본에서 제로 0과 길드 용병 3명의 `loyalty.value=0`, `dangerDays=3`을 설정하고 파견·영입 없이 날짜를 넘겼다. `m04`는 2일차, `m02`와 `m03`은 6일차에 무소속으로 이동했다. `m02`는 33일차에 `archon`으로 이동했고 비용이 318→517로 바뀌었다. 해당 날짜의 메모리 상태에 영입비만 채우고 영입하면 길드에 복귀하며 충성도는 60이었다. ## 자동 플레이

시드 순서는 `days`, `audit-20261120`, `audit-2`, `audit-3`, `audit-4`, `audit-5`. 각 시드에서 `npm run days -- 20 <시드>`, 40, 80을 각각 실행했다. 게임이 1일차에 시작하므로 80회 정산 직후 화면 날짜는 81일차다. 구간 합계는 살아남은 길드 소속 비주인공 기준이다.

| 정산 횟수 × 시드 | 최종 구간 합계 (높음/보통/낮음/위험) | 미납일 합계 | 거부/이탈 | 시설·훈련 |
|---|---:|---:|---:|---|
| 20 × 6 | 7/18/0/0 | 0 | 0/0 | 의무실 Lv1~2, 훈련소 Lv0~2, 탐지소 Lv1, 훈련 경험치 230 |
| 40 × 6 | 15/11/2/0 | 0 | 0/0 | 의무실 Lv2, 훈련소 Lv1~2, 탐지소 Lv1~2, 훈련 경험치 1,085 |
| 80 × 6 | 21/12/7/4 | 20 | 2/0 | 의무실 Lv2~3, 훈련소 Lv2, 탐지소 Lv2, 훈련 경험치 4,280 |

80회 후 `days`는 비주인공 9/9명이 높음, `audit-5`는 8/8명이 낮음·위험(4/4)이다. 여섯 시드가 같은 쪽으로 쏠리기보다는 결과가 갈린다. `audit-5`는 46~48일차, 64~66일차, 76~80일차에 연속 미납했다. 마지막 구간은 76·77일차에 부상 5·4명이 나온 연속 패배와 겹치며, 77~80일차에는 하루 107 제로씩 미납했다. 80일차 승리 보상은 당일 유지비 판정이 끝난 뒤 들어왔다. 80회 정산 뒤 잔액은 43 제로였다.

`npm run economy-sweep -- <20|40|80> 6`의 기본값 결과는 아래와 같다. 이 스크립트는 별도의 파견·영입 정책을 쓰고 시설을 건설하거나 훈련 배치하지 않는다. `days`와의 차이를 시설 효과로 바로 해석할 수 없다. 두 스크립트의 자동 플레이는 실제 최고 몬스터 레벨로 목적지를 정렬하므로, 탐지소에서 보이는 정보만 쓰는 UI 자동 편성과도 플레이 조건이 다르다. | 정산 횟수 × 시드 | 승리/패배 | 미납일 합계 | 최종 제로 평균 | 길드 인원 평균 |

시설 사용만 바꾼 보조 대조도 했다. `autoplayDay`를 그대로 쓰고 메모리 복제본에서만 건설 순서를 빈 목록으로 바꾸고 훈련 배치를 껐다. 80회×6에서 기본 시설 정책은 미납 20일·거부 2회·이탈 0회, 공사·훈련을 끈 쪽은 미납 67일·거부 26회·이탈 26회였다. 시설을 끄면 영입 가능한 시점도 달라지므로, 이 결과에는 유지비·편성·부상·승패의 연쇄 효과가 포함된다.

## 수치 의견

- 일괄 유지비 인하 판단은 보류할 만하다. 이미 현재 기본값은 3이고, `economy-sweep`의 ‘유지비 기본 3’ 행은 기본값과 완전히 겹친다. 80회×6의 경험치 40/20/10 조합은 기본값 대비 미납 67→50, 승리 191→219였지만 시설을 이용하는 플레이에서도 같은 방향인지 추가 비교가 필요하다.
- `audit-5`처럼 길드 규모가 커지고 고등급 연패가 겹치는 구간에서 흑자일 평균보다 **연속 미납 최대 일수**와 **당일 유지비 대비 현금 보유일**을 기준으로 공사·영입 정책의 준비금을 비교할 만하다.
- 충성도는 40회까지 위험 0명이었고 80회에는 두 극단이 모두 나왔다. 거부·이탈 확률을 한꺼번에 조정하기 전에, 같은 정책에서 주력과 대기 인원의 구간 변화 및 이탈 직전의 미납 횟수를 구분해 비교할 만하다.
