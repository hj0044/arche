# 지시서 017: UI 전면 개편 (시안 준수)

전제: 지시서 015와 016이 머지된 뒤에 시작한다. 이 지시서의 목적은 한 가지다. **사용자가 확정한 1차 시안(`docs/design/ui/`)과 같은 화면을 만든다.** 새로 디자인하지 않는다. 시안과 다르게 "더 낫게" 만들고 싶어도 만들지 않고 보고한다.

## 0. 이 문서를 읽는 순서와 원칙
1. `docs/design/ui/README.md`(준수 규칙 7개, 디자인 값), `docs/design/ui/contract.json`(화면별 구역 순서와 수치 규칙), `docs/design/ui/shots/ref/*.png`(시안 기준 스크린샷, 390×844 @2x), `docs/design/ui/*.html`(시안 원본)을 모두 읽는다.
2. **시안 HTML이 곧 스타일 명세다.** 시안은 인라인 스타일이라 간격, 글자 크기, 색, 모서리, 높이가 전부 그 안에 적혀 있다. 감으로 만들지 말고 해당 구역의 인라인 값을 읽어 옮긴다. 시안과 `shots/ref`, README가 서로 다르면 README → 시안 HTML → 스크린샷 순으로 믿고, 어긋남을 보고한다.
3. 위반 등급
   - **금지**(멈추고 보고): 구역 순서 변경, 정보 삭제, 색·크기·모서리·4열·5슬롯·탭 수 변경, 시안에 없는 화면 요소 추가, 시안 문구 변경.
   - **허용(기록 필수)**: 실제 데이터로 바뀌는 숫자·이름, 데이터가 없어 "—"로 두는 칸, 시안의 예시와 데이터 개수가 달라 생기는 차이(예: 특성 슬롯 수).
   - 금지에 걸리는 화면은 그 화면만 멈추고 나머지를 계속한다. 충돌은 PR 본문과 `docs/open-questions.md`에 한 번에 모아 보고한다(CLAUDE.md의 "설계서와 어긋나는 구현" 규칙).
4. 엔진 규칙, 수치, 저장 형식은 건드리지 않는다. 필요한 값은 화면용 선택자(`src/ui` 또는 `src/app`의 읽기 전용 함수)로 만든다. 엔진을 바꿔야 하는 일이 생기면 멈추고 보고한다.

## 1. 단계 (이 순서를 지킨다. 한 단계가 끝나면 커밋)
**A. 도구**를 먼저 만들고 나서 **B. 토큰**, **C. 부품**, **D. 화면**으로 간다. 도구 없이 화면을 만들지 않는다. 화면이 맞는지는 사람이 아니라 도구가 먼저 말해 주게 하기 위해서다.

### A. 검증 도구 (화면 작업 전에 완성)
1. 의존성: `@playwright/test`, `pixelmatch`, `pngjs`를 devDependencies에 추가한다(브라우저 설치 `npx playwright install chromium`은 로컬 작업용이며 `npm run build`와 Render 빌드에 넣지 않는다). 설치가 안 되면 멈추고 보고한다.
2. **UI 픽스처**: `scripts/make-ui-fixture.ts`가 시안의 예시를 닮은 상태를 만들어 `src/ui/fixtures/ui-mock.json`(세이브 JSON)에 쓴다. 조건: 12일차, 제로 1,240·아르케 86·고유 재료 3, 길드 계약자 20명(상태 다양: 대기·파견 중·훈련 중·부상·레벨업 가능·충성 낮음), 진행 중 파견 2건, 의무실 공사 중, **리프트 목록에 위험도 5구간(압도~무모)이 모두 한 번 이상** 나오게, 마감 D-1 리프트 하나, 도시 3곳. 숫자는 시안과 똑같을 필요는 없다. 앱은 개발 서버에서 `?fixture=ui`일 때만 이 세이브를 메모리 저장소로 불러온다(프로덕션 빌드에서는 동작하지 않게 `import.meta.env.DEV`로 막는다).
3. `npm run ui:shots`: Playwright(chromium, 390×844, deviceScaleFactor 2)로 ① 시안 12개를 `docs/design/ui/shots/ref/`에 다시 찍고(이미 올려 둔 것과 같아야 한다), ② 앱의 각 화면을 픽스처로 `docs/design/ui/shots/app/`에 찍고, ③ 좌우로 나란히 붙인 `shots/compare/<화면>.png`와 화면별 불일치 픽셀 비율을 `shots/report.json`에 쓴다(pixelmatch threshold 0.2). 글꼴이 로드될 때까지 기다린다(`document.fonts.ready`). 애니메이션은 끈다(`prefers-reduced-motion`).
4. `npm run ui:check`(Playwright 테스트, 픽스처 사용). 화면마다 아래를 자동 검사한다. **이 검사가 통과해야 화면이 끝난 것이다.**
   - **구역 계약**: `contract.json`의 `sections`가 `data-ui="<화면>.<구역id>"` 요소로 **같은 순서로** DOM에 있다(`optionalChildren` 구역은 안의 카드가 없을 수 있다). 계약에 없는 `data-ui` 구역이 있으면 실패.
   - **수치 계약**: 터치 대상(button, a, input, `[role=button]`, `[data-touch]`) 박스가 44×44 이상. 모든 글자 요소의 계산된 font-size가 11px 이상. 로고 줄 높이 44, 하단 탭 높이 64, 탭 4개와 이름 일치(탭 화면에서만 탭바가 있고 `tabBar:false` 화면에는 없다), 좌우 여백 16~20, 카드 모서리 14, 계약자 그리드 열 수 4, 파티 슬롯 줄당 5, 위험도 라벨이 5구간 이름 중 하나이고 5칸 막대가 함께 있다.
   - 터치 영역만 키우려면 바깥 요소를 44px로 하고 안쪽에 시안 크기의 시각 요소를 둔다(`data-touch`).
5. `npm test`(Vitest, 노드 환경)에 **정적 검사** 하나를 넣는다: `src/ui/**`에서 ① 헥스·rgb 색 리터럴이 `src/ui/theme.css`와 `src/ui/art/fallback/` 밖에 있으면 실패, ② 이모지 문자가 있으면 실패, ③ 화면 문구에 "용병"이 용어 표를 거치지 않고 직접 있으면 실패(`용병단`, `떠돌이 용병`은 허용), ④ `src/ui`가 `src/storage`를 직접 임포트하면 실패(저장은 `src/app`을 거친다).
6. `AGENTS.md`의 명령 목록에 `ui:shots`, `ui:check`, `make-ui-fixture`를 추가한다.

### B. 디자인 토큰
- README의 "디자인 값"을 `src/ui/theme.css`의 CSS 변수로 한 곳에 둔다(색, 위험도 5색, 속성색, 성장 한계 구간 테두리색, 특성 종류색, 모서리, 간격 8/12/16/20, 글꼴). 화면 CSS는 변수만 쓴다. SVG의 fill·stroke도 `var(--…)`나 `currentColor`.
- 글꼴은 Noto Sans KR 400/500/700(시안과 같은 Google Fonts 링크). 대체 글꼴 스택은 `'Noto Sans KR', system-ui, sans-serif`. `font-display: swap`.
- 구간 경계(성장 한계 40/45/50/55/65, 위험도 5구간 기준)는 색이 아니라 **수치이므로 데이터**다. 성장 한계 구간 경계와 구간 이름은 `src/data/ui.json`에, 위험도 구간 기준은 015에서 만든 `combat-power.json`을 읽는다. 색은 구간 id로 테마 변수와 이어 붙인다(`--cap-tier-3` 같은 식).
- 특성 종류(공통/역할/배경/고유/속성/종족)와 속성(7)도 id → 색 변수로 잇는다. 새 속성·종류는 데이터 행과 변수 한 줄로 늘어야 한다.

### C. 공통 부품 (`src/ui/components/`)
시안에 반복되는 것만 만든다. 이름은 영어, 화면 문구는 한글.
`LogoRow`(로고=홈 버튼 44px, 우측 슬롯, 톱니=설정), `TabBar`(4탭, 현재 탭 상단 강조선, 배지), `Card`, `Chip`/`ChipRow`(가로 스크롤), `RiskPill`(색 + 라벨 + 5칸 막대. 색만으로 구분하지 않는다), `Gauge`/`ProgressBar`, `MercCard`(성장 한계 구간 테두리·빛·보석, 경험치 막대, UP 배지, 상태 글자), `Slot`(파티 슬롯 +), `StatRow`, `TraitRow`(종류 칩, 잠금 행), `Section`(제목+목록), `Seg`(1x/2x/3x), `Toggle`, `Banner`(리프트 장면), `Icon`(인라인 SVG 모음, 시안의 아이콘을 그대로 옮긴다), `Art`(아래 그림 슬롯).
- 부품 하나에 시안의 해당 모양이 정확히 하나씩 대응하게 한다. 부품마다 `data-ui`를 받을 수 있게 만든다.

### D. 화면 (이 순서로, 화면마다 커밋 하나)
셸(탭바·로고줄·스와이프) → Main → Content(리프트 탭) → Party → Result → Merc → MercDetail → Battle → Base → Settings → Content의 탑·보스·영입 탭.
화면 하나의 작업 순서: ① 시안 HTML에서 해당 구역의 값을 읽는다 → ② 컴포넌트로 조립하고 `data-ui`를 단다 → ③ `ui:check` 통과 → ④ `ui:shots`로 compare 이미지를 보고 눈에 띄는 차이를 고친다 → ⑤ 커밋(`UI: <화면> 시안 적용`). `ui:check`가 실패하면 다음 화면으로 넘어가지 않는다.

## 2. 셸과 내비게이션
- 하단 탭은 4개: 홈·콘텐츠·계약자·거점. 현재 화면 `home→홈`, `rifts→콘텐츠`, `mercs→계약자`, `base→거점`. 기존 5번째 탭 "저장"은 없애고 **설정은 톱니**로 들어간다(`saves` 화면을 설정 화면으로 바꾼다). 계약자 탭 배지는 레벨업 가능 수.
- "하루 넘기기" 버튼은 **홈 화면에만** 있다(시안 Main). 다른 화면에서 지금 있는 "다음 날로" 버튼은 없앤다. 기능이 사라지는 것이 아니라 홈에서 한다.
- 파티·계약자 상세·전투·설정·하루 결과는 탭바가 없다(`contract.json`의 `tabBar:false`). 뒤로 가기 버튼이 있다.
- **스와이프 이동**(README [제안]이지만 이번에 구현한다): 탭 화면 4개 사이에서만. 가로 이동량 ≥ 60px이고 세로 이동량의 1.5배 이상일 때 이동. 가로 스크롤하는 칩 줄·슬롯 위에서 시작한 제스처와 화면 양 가장자리 20px 안에서 시작한 제스처는 무시. 화면 전환은 좌우 슬라이드 200ms, `prefers-reduced-motion`이면 즉시. 첫 탭에서 오른쪽, 끝 탭에서 왼쪽으로는 이동하지 않는다. Playwright로 터치 제스처 테스트를 넣는다.
- Title·NewGame 화면은 시안이 없다. 레이아웃은 그대로 두고 토큰·부품만 적용한다.
- 브라우저 뒤로 가기(History) 연동은 이번 범위가 아니다. 필요해 보이면 open-questions에 적는다.

## 3. 화면별 구현 메모 (자세한 모양은 시안, 구역 순서는 contract.json)
- **Main**: `levelUpOverview`, 마감 임박, 충성 위험, 시설 공사, 파견 진행률 등 지금 홈이 쓰는 선택자를 재사용한다. 오늘 할 일 카드는 해당하는 것만 보이고 시안의 카드 4종이 최대다. 해당하는 카드가 하나도 없을 때의 빈 상태는 시안에 없다. 이때는 "오늘 할 일" 구역 전체를 숨기고 open-questions에 기록한다.
- **Content**: 도시 칩과 위험도 5구간 개수 칩은 목록 필터로 동작(현재 `riftFilter.ts`를 재사용). 카드의 위험도는 **015의 5구간 추정**을 쓴다. 배너 장면은 그림 슬롯.
- **Party**: 슬롯 5개씩 두 줄, 후보는 4열. 하단 요약(전투력·위험도·승률 범위·구성 보너스)은 `computeEffectiveStats`를 쓰는 기존 전투력·위험도 함수에서 가져온다(016 이후). 자동 편성 버튼 유지.
- **Merc**: `mercFilter.ts`(검색·초성·정렬·필터·일괄 레벨업)를 재사용. 카드 테두리는 성장 한계 구간(데이터), 경험치 막대는 다음 레벨까지의 비율. "UP"은 레벨업 가능.
- **MercDetail**: 016의 최종 스탯 9개와 충성도, 특성 슬롯. 시안의 "특성 3/4 해금" 같은 숫자는 예시다. **슬롯 수와 해금 수는 데이터(성장 한계 → 슬롯 수)로 표시**하고 잠긴 슬롯은 시안의 잠금 행 모양을 쓴다(허용 차이, 기록).
- **Battle**: 기존 재생 로직·속도·건너뛰기·한 턴씩·일시정지는 유지하고 모양만 시안으로. 재생 속도는 시안의 1x/2x/3x에 맞춰 `ui.json`의 `replay.speeds`를 `[1,2,3]`으로 바꾼다. 시안에 없는 기능을 지금 전투 화면이 갖고 있으면 지우지 말고 3.1의 규칙을 따른다.
- **Base**: 시설 카드 3종과 잠긴 카드, 훈련 배치 요약. 시설 강화·훈련 배치 조작은 기존 기능 유지(카드 안의 버튼 또는 상세).
- **Settings**: 슬롯 규칙(자동 저장 슬롯별 최근 3개 순환, 수동 슬롯 개수 제한 없음, 덮어쓰기 확인)은 그대로. 전투 재생 속도·소리·중요 행동 확인은 **기기 설정**이라 세이브 파일에 넣지 않고 `src/app`의 설정 저장(브라우저 로컬, 인터페이스로 분리)에 둔다. 소리는 아직 소리가 없으므로 값만 저장하고 효과는 없다(토글 옆에 "준비 중" 표기 금지: 시안에 없으므로 그대로 두고 open-questions에 기록). **"중요 행동 확인"은 덮어쓰기 확인을 끌 수 없다**(AGENTS.md 1단계 범위의 확정 규칙). 끌 수 있는 것은 철수 같은 다른 확인뿐이다. 이 해석을 open-questions에 적는다. 저장 형식 버전 표시는 `SAVE_VERSION` 상수에서 읽는다.
- **Tower / Boss**: 엔진에 없는 [제안] 콘텐츠다. 콘텐츠 화면의 서브 탭 모양은 시안대로 두되, 탑·보스 탭을 누르면 "준비 중" 빈 화면(시안의 헤더·탭 유지)을 보여 준다. 시안 `Tower.html`, `Boss.html`은 나중 지시서가 쓴다.
- **Recruit**: 엔진에 영입 기능이 있으면(`src/engine`을 확인) 시안 `Recruit.html`의 목록·필터·카드 모양으로 연결하고, 데이터가 모자란 칸("???" 등 시안의 잠긴 표현)은 시안 규칙대로 한다. 영입이 이미 다른 화면(계약자 등)에 있으면 중복해서 만들지 말고 어디에 연결했는지 보고한다. 엔진에 없으면 Tower·Boss와 같이 "준비 중".
- 모든 화면의 숫자·문구는 용어 표(`terms.json`)와 데이터를 읽는다. 하드코딩 금지.

### 3.1 시안에 없는 기존 기능
현재 앱에는 있지만 시안에 자리가 없는 기능(예: 철수 버튼, 보고서 목록, 저장소 용량 경고, 새 게임 확인 등)이 있을 것이다. 기능을 지우지 않는다. 처리 순서: ① 시안의 해당 구역 안에서 쓰이는 컴포넌트(카드 탭 → 상세, 확인 대화상자, 토스트, 바텀 시트 등)로 자연스럽게 흡수할 수 있으면 그렇게 한다. ② 시안의 구조를 바꿔야만 넣을 수 있으면 넣지 말고 목록으로 보고한다(사용자가 시안을 고치거나 위치를 정한다). 이 목록을 PR 본문에 "시안에 없는 기능" 표로 싣는다.

## 4. 그림 슬롯 (임시 SVG를 이미지 교체형으로)
- `Art` 부품 하나로 모든 그림을 받는다: `<Art kind="portrait|banner|emblem|boss|icon" id="..."/>`. 이미지 경로 규칙은 `public/art/<kind>/<id>.webp`(없으면 `.png`, `.svg` 순). 경로 규칙과 비율을 `src/data/ui.json`의 `art`에 데이터로 둔다(비율은 시안에서 읽는다: 초상, 리프트 배너 350:84, 길드 배너, 보스, 엠블럼).
- 파일이 없거나 로드 실패 시 **대체 그림**을 그린다. 대체 그림은 시안의 임시 SVG를 `src/ui/art/fallback/`로 옮겨 쓴다(초상은 역할·속성에 맞는 색 변형, 배너는 리프트 종류별). 이 폴더만 색 리터럴을 허용한다.
- 나중에 `public/art/` 안에 파일만 넣으면 화면이 바뀌어야 한다. 그 방법을 `docs/art-guide.md`에 한 페이지로 쓴다(경로, 비율, 권장 크기, 파일 이름은 데이터의 id).
- 이미지 지연 로딩, 자리 고정(레이아웃 이동 없음: 항상 비율 박스).

## 5. 접근성과 입력
- 색만으로 상태를 구분하지 않는다(위험도는 라벨+막대, 상태는 글자, 성장 한계 구간은 테두리 모양과 보석 표시).
- 키보드 포커스 표시 유지(`:focus-visible`). 버튼에 의미 있는 `aria-label`(아이콘만 있는 버튼 포함: 톱니, 뒤로).
- 한 손 조작: 주요 행동 버튼은 화면 아래쪽(시안 위치)에 둔다.

## 6. 하지 않는 것
- 시안에 없는 화면과 기능, 탑·보스의 실제 규칙, 소리 구현, 애니메이션 확장, 테마 전환(라이트 모드), 엔진·수치·세이브 형식 변경(016에서 올린 버전 그대로), 브라우저 History 연동, 이미지 파일 제작.

## 7. 보고 (PR 본문)
1. 변경 요약과 `npm test`, `npm run ui:check`, `npm run typecheck`, `npm run build` 결과.
2. **화면별 표**: 화면 | 계약 검사 통과 | 불일치 픽셀 비율(`report.json`) | 허용 차이 목록 | 금지 충돌(있으면 멈춘 상태).
3. `shots/compare/*.png` 12장(또는 변경된 화면 전부)을 PR에 첨부한다.
4. "시안에 없는 기능" 표(3.1), "데이터가 없어 비워 둔 칸" 표(시안 요소 | 필요한 데이터 | 현재 엔진 상태).
5. 구현자가 정한 사항과 설계서·시안과 어긋나는 곳은 `docs/open-questions.md`에도 적는다.

## 8. 검수 방법 (Codex·Claude·사용자)
- 누구든 `npm run ui:shots`로 compare 이미지를 다시 만들 수 있다. 사용자는 PR에 첨부된 compare 이미지만 봐도 된다.
- 불일치 비율은 참고치다(예시 데이터와 실제 데이터가 달라 글자는 다를 수 있다). 합격 기준은 **`ui:check` 통과**와 **compare 이미지에서 구조·색·간격이 같다는 것**이다. 불일치가 큰 화면은 원인을 표에 적는다.
- 검수자는 `docs/design/ui/contract.json`의 구역 순서, 수치 규칙을 기준으로 위반을 `docs/reviews/`에 남긴다(양식 TEMPLATE.md). UI/UX 의견은 시안 변경 제안으로 따로 적는다(구현자가 반영하지 않는다).

## 9. 완료 조건: 머지와 배포까지 (AGENTS.md "구현 원칙"의 확정 규칙, 이 지시서의 일부)
**PR을 여는 것은 끝이 아니다.** 아래를 모두 마쳐야 완료다. 사용자의 확인을 기다리지 않는다.
1. `npm test`, `npm run ui:check`, `npm run typecheck`, `npm run build`가 통과한 PR을 연다.
2. 바로 `main`에 머지한다. 결정이 필요한 항목(시안 충돌, 데이터 공백)은 PR 본문과 `docs/open-questions.md`에 적되 **머지를 막지 않는다.** 시안과 충돌해 멈춘 화면은 그 화면만 기존 모습으로 두고 나머지를 머지한다.
3. Render 배포가 `live`가 될 때까지 확인한다(배포 상태 조회, 안 되면 사이트 응답 확인). 실패하면 원인을 고쳐 다시 머지한다.
4. 최종 보고는 "배포 완료"와 배포 커밋, 위 7번 보고 항목, 미해결 충돌 목록으로 한다.
