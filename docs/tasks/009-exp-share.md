# 지시서 009: 파견 경험치 총량 나누기

파견 한 번이 주는 경험치를 파티원이 나눠 갖게 한다. 정본은 설계서의 육성(경험치) 부분과 변경 로그 2026-11-20 마지막 행이다. 문서와 코드가 다르면 문서가 맞다. [확정]은 지켜야 하는 규칙, [제안]은 바꿔도 되지만 보고, [미정]은 구현하지 말고 질문한다. 충돌하거나 비어 있는 곳은 임의로 정하지 말고 `docs/open-questions.md`에 적고 보고한다.

## 배경

지금은 파티원 전원이 같은 경험치를 각자 받는다. 1명이 가든 5명이 가든 한 명당 양이 같아서, 큰 파티가 총경험치에서 무조건 이득이다. 소수 정예 파견이 불리하지 않게 총량을 나눈다.

## 규칙 (사용자 결정, 2026-11-20)

- [확정] 파견 경험치는 총량이 정해져 있고 참가자가 나눠 갖는다. 인원이 적으면 한 명당 몫이 늘어난다.
- [제안] 기준 인원 5: 총량 = 지금 한 명당 경험치 × 기준 인원. 한 명당 몫 = 총량 ÷ 파티 인원. 그래서 5인 파견은 지금과 같다.
- [제안] 한 명당 상한: 지금 한 명당 경험치의 2배까지. 1~2인 파견이 과하게 이득이 되지 않게 한다.
- 파티 인원은 그 파견에 나간 전원이다(개방자 주인공 포함). 부상으로 쓰러진 사람도 인원에 센다.
- 계산식: `perMember = round(expByOutcome × tierMult × levelMult)`(기존 식 그대로), `share = min(perMember × basePartySize ÷ partySize, perMember × soloCapMultiplier)`, 소수점은 반올림.
- 예(기준 인원 5, 상한 2배): 5인 ×1.0, 4인 ×1.25, 3인 ×1.67, 2인 ×2.0(상한), 1인 ×2.0(상한).

## 작업 목록

### 1. 데이터
- `progression.json`에 `expShare`를 추가한다: `basePartySize` 5, `soloCapMultiplier` 2. 코드에 5나 2를 박지 않는다.
- 값을 바꾸면 규칙이 바뀌어야 한다(예: 기준 인원 4, 상한 3배).

### 2. 엔진
- 귀환 정산의 경험치 계산(`game.ts`, `expGains` 만드는 곳)을 위 식으로 바꾼다. 순수 함수로 분리하면 테스트하기 쉽다.
- 경험치는 시드와 무관하게 결정적이다(전투 결과가 같으면 같은 값).
- 보고서(`ExpGain`)에 기록되는 값은 나눈 뒤의 값이다.

### 3. 화면
- 파티 편성 화면에서 "예상 경험치(한 명당)"를 보여준다. 인원을 바꾸면 값이 바뀐다. 승리 기준이다.
- 파견 보고서에는 지금처럼 한 명당 받은 경험치만 보여준다.

### 4. 테스트
- 5인 파견은 변경 전과 같은 값이다(회귀 테스트).
- 3인은 5/3배, 4인은 1.25배, 1~2인은 상한 2배.
- 데이터 값을 바꾸면(기준 인원 4, 상한 3배) 결과가 따라 바뀐다.
- 패배와 후퇴도 같은 식을 따른다(결과별 기본값에 같은 나누기 적용).
- 기존 결정성 회귀 테스트가 새 값으로 갱신되어도 같은 시드에서 두 번 돌려 같은 결과가 나온다.

### 5. 도구
- `npm run days`와 `npm run economy-sweep`의 자동 플레이는 최대 5인 파견이라 결과가 거의 안 바뀔 수 있다. 바뀐 점이 있으면 보고한다.
- 수치 조정은 하지 않는다. 밸런스는 사용자의 플레이 이후에 정한다.

## 하지 않는 것
- 인원별 비율 표(완만한 차등)는 만들지 않는다. 플레이 후 필요하면 그때 얹는다.
- 충성도 변동, 보상(제로, 아르케, 재료) 분배는 건드리지 않는다. 이 지시서는 경험치만 다룬다.
