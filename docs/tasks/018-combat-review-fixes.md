# 지시서 018: 전투·전투력 검수 반영 (오류 수정, 데이터 조정, 전투 변동성 개선)

근거: `docs/reviews/2026-11-24-combat-power-sim.md`(Codex 검수, 재현 스크립트·CSV는 `docs/reviews/data/combat-power-2026-11-24/`). 이 지시서는 ① 확실한 오류 수정, ② 위험이 낮은 데이터 조정, ③ **설계 판단에 따른 전투 변동성 개선(실험 후 채택)**을 한다. 특성 수치 하향 등 나머지는 사용자 플레이 후에 정한다.

**병렬 작업 주의**: 지시서 017(UI 개편)이 `src/ui/`를 바꾸고 있다. 이 지시서는 **`src/ui/`를 수정하지 않는다**(엔진, 데이터, 스크립트, 테스트, 문서만). UI에서 불러야 할 곳이 생기면 호출 위치를 보고만 한다.

## 1. 오류 수정 (필수, 데이터 조정과 무관하게 고친다)
1. **파티 전투력의 아군 특성 누락** (`src/engine/combatPower.ts`, 전투 `combat.ts`). 파티 전투력은 전투 시작 때와 같은 방식으로 파티 전체의 시작 효과(아군 대상 특성)를 반영해야 한다. 지금은 자기 자신이 내는 효과만 반영해서 같은 편성이 전투에서는 832, 표시는 826이다. 전투 시작 스탯 계산과 전투력 계산이 **같은 함수**를 쓰게 만든다(016 §4 "한 곳"의 원칙). 테스트: 리포트의 재현 사례(`core` 검사의 `power_party_aura`: Lv35 전술가 `unique_m26`와 수호자, 체력 특성 +5%)에서 두 값이 같다.
2. **위험도 캐시 키에 특성이 없음** (`combatPower.ts`의 위험도 캐시). 키에 활성 특성 id와 단계(`traitRanks`), 스킬 id, 레벨, 최종 스탯을 포함한다. 테스트: 같은 스탯에서 특성만 추가한 뒤 조회하면 캐시를 비운 결과와 같은 단계가 나온다(`risk_cache_trait_key`: 시드 `power:cache:15:84:0–11`, 마도사 Lv15 에너지공격 84, 중급 Lv15 균열 술사 둘).
3. **치명타 피해율 최종 상한 누락** (`src/data/stats.json`, `src/engine/stats.ts`). 데이터에 `caps.critDmg: 2.0`을 추가하고 `computeEffectiveStats`의 최종값에 적용한다(치명타율 0.8, 회피율 0.5 상한은 그대로). 데이터 검증이 상한 키 누락을 실패로 잡는다. 테스트: 입력 10.0이 2.0으로 잘린다. 현재 30명 중 잘리는 계약자는 없다(최대 합산 1.75)는 것도 테스트로 둔다. 상한 값 2.0은 [제안] 임시값이다.

## 2. 전투력 가중치 조정 (데이터만)
- `src/data/combat-power.json`의 `statWeights`를 아래로 바꾼다. 리포트에서 예산(95~105%)을 30명 모두 지키면서 검증 오차가 26.17 → 22.99%p로 줄어든 후보다.
  `{ "hp": 0.1875, "pAtk": 2.5, "eAtk": 2.5, "pDef": 1.5, "eDef": 1.125, "spd": 1.25 }` (치명타·회피 기댓값 식은 그대로).
  - 기존 `atk` 하나로 쓰는 곳이 있으면 `pAtk`·`eAtk`로 나눈 가중치를 읽게 한다(구조 변경은 최소로).
- **전투력의 의미를 문서로 못박는다**(데이터 `_note`와 `docs/open-questions.md`): 전투력은 **표시와 계약자 예산을 위한 지표**이고 개별 전투의 승률 예측기가 아니다. 위험도는 계속 모의 전투로 정한다. 리포트상 전투력 비율만으로는 평균 26%p 틀리는 것이 정상 범위다.
- 변경 후 `npm run balance`(전투는 영향 없어야 한다), `risk-check`, `difficulty-stats`를 다시 돌려 전후를 적는다. 자동 편성이 전투력을 쓰고 있다면 그 결과 변화도 적는다.

## 3. 위험도 모의 횟수: 상세 평가는 더 많이 (엔진 + 데이터, UI는 건드리지 않음)
- 리포트: 12회 → 96회에서 단계 일치율이 93.4% → 97.5%(48회는 95.1%).
- `combat-power.json`에 `detailSimulations: 96`을 추가하고, 위험도 추정 함수가 선택 인자(예: `detail: true`)로 이 횟수를 쓰게 한다. **기본(리프트 목록)은 지금처럼 12회**를 유지한다.
- 한 번의 상세 평가가 걸리는 시간을 측정해 보고한다(Node 기준 ms). 목록 12회 대비 8배이므로 모바일에서 문제인지 판단할 근거로 쓴다.
- 파티 편성 화면 요약에서 `detail: true`를 쓰는 연결은 **017이 머지된 뒤** 한다. 지금은 호출 위치를 목록으로 보고하고 연결하지 않는다.

## 5. 전투 로직 개선: 승패의 결정성을 낮춘다 (설계 판단, 실험으로 채택)
**진단**(리포트에서 직접 읽은 것): 365개 조합 중 135개는 2,000회 모두 지고 81개는 모두 이겼다. **10~90% 승률인 조합은 59개(16.2%)뿐**이다. 평균 곡선은 매끄럽지만(전투력 비 0.9~1.0에서 43.5%, 1.0~1.1에서 56.4%) 같은 편성끼리 싸우면 결과가 거의 정해져 있다. 그래서 "접전" 칸이 좁고, 접전·우세 리프트가 있는 날이 47%에 머문다(015 목표 80%). 또 속도는 한 칸 차이로 행동 순서가 바뀌는 지점에서 승률이 급변한다(저격수 속도 상한 +14.05%p, 사제 속도 하한 +19.15%p). 이것은 버그가 아니라 **전투가 너무 결정적이라는 설계 문제**다. 공급을 늘리는 것(4번)만으로는 한계가 있으니 전투 쪽 변동성을 함께 조정한다.

실험은 두 레버뿐이다. 둘 다 평균 전투력 균형은 그대로 두고 결과의 흩어짐만 키운다.
1. **피해 변동 폭**: `combat.json`의 `damage.varianceMin/Max`(지금 0.9/1.1). 후보 `0.85/1.15`, `0.80/1.20`, `0.75/1.25`. 데이터만 바꾼다.
2. **행동 순서 흔들림(initiative jitter)**: 라운드 시작에 유닛마다 속도에 `±speedJitter` 비율의 작은 난수를 더해 순서를 정한다(실제 스탯은 변하지 않는다). `combat.json`에 `speedJitter`(후보 0, 0.05, 0.10)를 둔다. **0이면 지금과 같은 동작**이어야 한다. 난수는 **전용 스트림**(`시드:init`)에서 유닛 수만큼 항상 같은 개수를 뽑아 결정성 규칙(같은 시드 = 같은 결과, 소비량이 값에 따라 달라지지 않음)을 지킨다. 이 동작은 설계서에 없는 규칙이므로 `docs/open-questions.md`에 적는다.

**실험 방법**: `scripts/variance-sweep.ts`를 만든다(재현 가능, 검수 리포트의 `docs/reviews/data/combat-power-2026-11-24/audit.ts` 표본 방식을 참고해도 된다). 후보 조합(변동 폭 4종 × 흔들림 3종 = 12개, 기준 포함)마다 아래를 잰다. 시드는 조합당 충분히(전투 조합 365개 × 800회 이상, 진행은 20개 시드) 쓴다.
- M1: **승률 10~90%인 조합의 비율**(기준 16.2%).
- M2: **접전 또는 우세 리프트가 있는 날 비율**(`difficulty-stats`, 20개 시드. 기준은 4번 적용 후의 값을 새로 잰다).
- M3: **안전·무모 보호선**: ① 5인 vs 상급×4(Lv1/10/30/50/70), 5인 Lv5 vs 중급 Lv15×3, 5인 Lv30 vs 중급 Lv40×3의 승률이 기준보다 **5%p 넘게 떨어지지 않는다**(압도는 압도로 남는다). ② 시작 4인 Lv5 vs 중급 Lv15×3 승률이 10%를 넘지 않는다(무모는 무모로 남는다).
- M4: **속도 민감도**: 저격수 속도 상한, 사제 속도 하한, 마도사 속도 상한 각각의 승률 변화(기준 +14.05, +19.15, +13.45%p)가 줄어드는가.
- M5: **위험도 일치율**: 12회 모의 대 96회 모의 단계 일치율이 기준(93.4%)보다 3%p 넘게 떨어지지 않는다(변동이 커지면 12회 추정이 더 흔들릴 수 있다).
- M6: 한 전투의 평균 라운드 수, 15라운드 철수 비율(기준 2.75%), 복귀 성공률, 부상 계약자·일.

**채택 규칙**(구현자가 판단하지 말고 이 규칙을 따른다):
1. M3 ①②와 M5를 모두 지키는 후보만 남긴다. 결정성 테스트가 통과해야 한다.
2. 남은 후보 중 **M2가 가장 높은 것**을 채택한다. 동률(차이 1%p 이내)이면 변경이 더 작은 쪽(변동 폭이 좁고 흔들림이 작은 쪽)을 고른다.
3. 채택한 값이 기준보다 M1을 **1.5배 이상** 늘리지 못하거나 M2를 **3%p 이상** 올리지 못하면 효과가 없는 것이니 **기준값을 유지**한다(데이터를 바꾸지 않는다). 흔들림 코드는 `speedJitter: 0`으로 남겨 두고 이유를 보고한다.
4. 채택하든 안 하든 12개 후보의 M1~M6 표 전체를 PR과 `docs/reviews/`에 남긴다(사용자 판단 자료).
5. 채택 후 `npm run balance`의 45개 구성 중 M3 ①②가 아닌 구성의 승률은 다를 수 있다. 달라진 구성 목록과 크기를 보고한다(016의 ±5%p 기준은 이번에 한해 위 M3 보호선으로 대체한다. 사용자 결정 2026-11-24 "전투 로직 개선안까지").
6. 같은 PR에서 위험도 5구간 경계와 15라운드 철수 규칙은 바꾸지 않는다.

## 7. 이번에 하지 않는 것 (보류, 이유와 함께)
리포트의 P3 항목은 **사용자 플레이 후** 정한다. 이유: 특성 A/B는 승패가 갈리도록 고른 상대에서 잰 값이라 효과가 부풀 수 있고, 지금 값을 깎으면 016 보존 기준(±5%p)을 다시 맞춰야 한다.
- 체력 특성 하향(대지의 힘 0.08→0.06, 지켜내는 자 0.10→0.08, 강건함 0.06→0.04), 폭주 상한(`unique_m12` 최대 0.25), 노련한 지휘 속도, 속성 친화 값, 역할 속도 바운더리.
- 15라운드 철수 규칙, 위험도 경계값(0.90/0.75/0.50/0.25), 역할 기본값, 계약자 30명 숫자, UI.
- **타깃팅 규칙 변경**(전열이 공격을 독점해 수호자 체력·회피가 지나치게 큰 영향을 주는 문제: 체력 ×1.10 → +18.5%p, 회피 +5%p → +11.5%p). 후열 피격 확률 같은 해결책은 설계서 §5의 전열·후열 규칙을 바꾸는 일이라 사용자 결정이 필요하다. `docs/open-questions.md`에 **결정 대기**로 적는다.
- 사제 AI(치유 임계 0.7)와 스킬 선택 규칙 변경.
- 리포트의 관찰(참고): 수호자·사제·전술가는 1대1에서 못 이긴다(역할 의도상 정상), 오진석(수호자) 대 마커스 홀리스(수호자)처럼 같은 역할 안의 강함 차이가 크다(Lv35 추가 효과 +89.3 대 +22.3%p). 이 격차는 보류 항목이지만 `docs/open-questions.md`에 **결정 대기**로 적는다.
- 접전 공급을 가용 인원수에 맞추는 구조(리프트 공급 로직 변경)는 별도 지시서(019 후보)다. 지금은 위 4번의 데이터 한 줄만 한다.

2. 사용자 확인을 기다리지 않고 바로 `main`에 머지한다. 결정이 필요한 항목은 PR 본문과 `docs/open-questions.md`에 적되 머지를 막지 않는다. 017과 같은 파일이 겹쳐 충돌하면 017을 우선하고 이 PR을 다시 맞춘다.
3. Render 배포가 `live`가 된 것을 확인한다. 실패하면 고쳐 다시 머지한다.
4. 최종 보고: "배포 완료", 배포 커밋, 1~5번 각각의 결과(전후 표 포함), 5번의 12개 후보 표와 채택 결과(또는 유지 사유), 상세 평가 시간 측정, 호출 위치 목록, 결정 대기 항목.
