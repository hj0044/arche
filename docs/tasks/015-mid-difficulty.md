# 지시서 015: 중간 난도 리프트 보강, 부상·마감 표기, 난도 분포 측정

배경: 사람 플레이(서울·개방자 16일, 7회 파견 5승 2패)와 자동 플레이 측정 모두에서 균열(안전)과 관문(무리) 사이에 고를 중간 선택지가 없었다. Claude와 GPT 토론의 1차 합의안이다. 옛 세이브는 신경 쓰지 않는다(AGENTS.md).

## 확정된 것 (사용자·토론 합의, 2026-11-22)
- 중간 난도 리프트를 데이터로 먼저 보강한다: 상위 균열, 하위 관문, 2~3인용 소규모 리프트.
- 예비 용병 전용 의뢰와 도시 계약은 만들지 않는다(보류).
- 부상과 마감 표기를 고친다(아래 2).
- 위험도를 5구간으로 바꾼다(아래 0). 초기 기준: 파견을 결정할 수 있는 날(출전 가능 인원이 있는 날)의 80% 이상에서 목록에 "접전 또는 우세(승률 50~90%)" 리프트가 있다.

## 작업 목록

### 0. 위험도 5구간 (표기·데이터, 사용자 확정 2026-11-23 후보안)
- `combat-power.json`의 `riskTiers`를 5구간으로 바꾼다. 이름과 경계는 데이터이고 임시값이다: 압도(승률 ≥ 0.90) / 우세(≥ 0.75) / 접전(≥ 0.50) / 열세(≥ 0.25) / 무모(그 미만). 기존 id `safe/fair/risky/hopeless`는 `crush/safe/fair/risky/hopeless`처럼 5개로 늘리되 구현자가 정하고 기록한다.
- 화면 표시 이름은 기존 안전·해볼 만·위험·무리 대신 위 이름을 쓴다. 색은 압도 초록, 우세 연두, 접전 노랑, 열세 주황, 무모 빨강. 색만으로 구분하지 않도록 라벨 옆에 5칸 막대(구간 단계 1~5)를 같이 둔다.
- "공략 가능" 판정(`ui.riftPlayableRiskTiers`)과 `riftFilter`의 기준은 기존 의미(해볼 만 이상)를 유지해 `접전 이상`으로 옮긴다. 필터·요약 문구의 "안전/해볼 만" 글자를 모두 새 이름으로 바꾼다. 테스트의 기대값과 문구도 갱신한다.

### 1. 중간 난도 리프트 (데이터 중심 [제안], 수치는 모두 임시값)
- 현재: 균열 몬스터 레벨 1~30·적 2~3, 관문 15~50·적 3~4. 8일차에 안전한 균열 3개와 무리인 관문 3개로 갈렸다.
- 목표: 어느 날에나 목록에 "접전·우세"가 1~2개 있다. 지금 용병 수준에서 "접전·우세"인 상위 균열과 하위 관문이 나오게 하고, 적 1~2명짜리 소규모 리프트(2~3인 파티에 맞는 것)를 일부 넣는다.
- 방법은 구현자가 정하되 코드가 아니라 데이터로 한다: 등급(`rift-tiers.json`)의 레벨 구간·적 수·가중치 조정, 도시별 `levelSkew`·`tierWeights` 조정, 필요하면 등급 안에 변형(레벨 구간·적 수 범위를 가진 행)을 두는 방식. 새 등급 이름을 만들지 않는다(설정집의 균열·관문·항로를 지킨다). 속성은 1단계 규칙대로 전부 공허.
- 이름 목록은 013의 것을 그대로 쓴다.
- 보상은 바꾸지 않는다. 다만 보상과 부상 부담은 다음 라운드의 비교 실험 대상이니 **데이터 한 곳에서 배율을 바꿀 수 있게** 둔다(등급·변형별 보상 배율, 부상 일수 배율 같은 값을 코드에 박지 않는다).

### 2. 표기 정리 (UI)
- **부상**: 용병 목록·홈·상세의 `경상 1일`은 `13일차부터 출전`처럼 날짜로 표시한다. 남은 일수 표현을 날짜로 바꾸되 이미 회복한 용병은 표시하지 않는다.
- **마감**: 코드는 `오늘 + 이동일 ≤ 마감일`일 때만 보낼 수 있다(`expedition.ts`의 마감 검사). 즉 "출발 마감"이 아니라 **이동일을 포함해 도착이 마감일 안**이어야 한다. 리프트 카드·상세에 `마감 D-n`은 유지하고, 상세와 파견 화면에 "이동 N일 포함, 늦어도 ○일차까지 출발"을 보여준다. 거점이 아닌 도시의 리프트에서 특히 헷갈리지 않게 한다.
- **보상**: 리프트 카드와 상세에 보상 총액과 함께 **파견 하루당 수익**(제로 기준, 이동 왕복 포함 총일수로 나눔)을 보여준다. 탐지소 레벨이 낮아 보상이 범위로 보이면 하루당 수익도 범위로 보이되 숨은 값을 드러내지 않는다(012 §6-1과 같은 원칙).

### 3. 측정 도구 (`npm run rift-stats` 확장 또는 새 도구)
자동 플레이 정책으로 날마다 목록을 평가해 아래를 보고한다(시드 6개 이상, 60일).
- 분모: 출전 가능 인원이 있어 파견을 정할 수 있는 날. 그날 실제로 편성할 수 있는 파티 기준.
- 목록의 위험도 분포를 압도(≥90)·우세(75~90)·접전(50~75)·열세·무모로 나눠, 각 구간이 목록에 있는 날의 비율.
- "접전 또는 우세(50~90) 있는 날" 비율(목표 80% 이상), 실제 선택률(구간별), 부상으로 출전 못 한 일수.
- 변경 전(`origin/main` 기준)과 변경 후를 같은 표에 나란히 보고한다. 수치는 목표(80%)에 닿도록만 조정하고 다른 것은 건드리지 않는다.

### 4. 테스트
- 마감 표기: 거점·타 도시 리프트에서 "늦어도 ○일차까지 출발"이 `마감일 − 이동일`과 일치한다.
- 부상 표기: 회복일이 13일차면 `13일차부터 출전`으로 나온다.
- 하루당 수익: 총일수(소요 + 왕복 이동)로 나눈 값과 일치하고 범위 표시에서 숨은 값이 새지 않는다.
- 새·변경 데이터 행으로 리프트가 생성되고 결정적이다(같은 시드, 같은 결과).

## 하지 않는 것
- 예비 용병 전용 의뢰, 도시 계약, 선점 경고, 새 리프트 등급 이름, 보상·부상 수치의 실제 조정(이번엔 배율을 바꿀 자리만 만든다).
